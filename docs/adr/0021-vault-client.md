# ADR-0021 — One vault client per vault root; per-vault reads are views over it

- **Status**: Accepted
- **Date**: 2026-10-19

## Context

[ADR-0020](0020-per-vault-state-in-the-daemon.md) put every vault's shared state in the daemon's vault entry and made the session a client of it: one connection and one one-way switch per process, an attach per connection epoch without a detach, and an in-process fallback that runs the same `src/lib/vault-entry/` module. Its closing constraint says per-vault state does not get its own connection, its own fallback switch or its own detach call. That was a rule, not a structure, and the session side wrote the same path out by hand three times: the corpus reads (#182, a daemon and a local semantic backend), the lexical leg (#184, a daemon and a local lexical reader), and the embedding provider's handshake. Every daemon facade re-implemented the switch branch (`ensure() === 'local' ? local() : wire`) with its own `local ??=` memo. Attach per epoch was written twice, and the `NOT_ATTACHED` forget four times. Each local facade was a hand-kept second copy of what the daemon's `vault`, `corpus` and `lexical` services already do (validate, call `VaultEntries`, map the entry's errors to the wire's codes), and the in-process side carried a fixed connection id, `LOCAL_CONNECTION_ID`, because the whole `VaultEntries` surface is keyed by a connection. The next per-vault read, the wikilink graph in the daemon (#172), would have cost about 18 files of plumbing before its consumers changed.

[ADR-0018](0018-shared-services-daemon.md)'s constraint still holds: a shared capability is a namespaced service plus a session-side facade over an interface the session already depends on, with an in-process fallback. This decision is about how that facade is built for per-vault reads.

## Decision

Give each vault root one **vault client** per side, and build every per-vault read as a view over it. This is the end state once #193 completes; the first PR builds the client and moves the corpus reads onto it, and the lexical leg follows in the second (see **Delivered in two steps** under Consequences).

- **One client per vault root and side.** `IVaultClient` (`src/modules/semantic/vault-client/`) is to be the session's only path to a vault entry: `call(method, params)` runs one read under the key this side attached, `status(profile)` reads a profile's status and never rejects, `warm()` attaches ahead of the first call, `dispose()` releases what the client built itself. `createVaultClients` builds one per vault root on the daemon side and one on the in-process side, on first use. Once #193 completes every reader of the vault goes through it; after the first PR the semantic backend does, and the lexical readers share only the client's attachment.
- **One typed method table.** `VaultMethods` in `src/daemon/protocol.ts` has one row per per-vault read (`corpus.nearest`, `corpus.nearestBlocks`, `lexical.search`), each the wire's existing params and result types; `call` is typed by it and adds the vault key itself. `vault.attach` and `vault.status` are not rows: they are the client's lifecycle. It is an `interface`, so a new row is one declaration.
- **The core owns the per-vault rules once.** `createLinkedVaultClient`, over one link (`{ epoch, request }`), owns the attach per connection epoch (one attachment over an epoch gate: concurrent callers share one `vault.attach`, an answer from a replaced connection records nothing), the vault key, the per-method timeouts, the `NOT_ATTACHED` forget and the status placeholders. The socket adapter, `createDaemonVaultClient`, wraps that core over the process's one connection and, once the lexical reader is a view, is the only place per vault that consults the one-way switch, starts the background attach while the switch is undecided, and meets transport failures. After the first PR the legacy daemon lexical reader still runs `services.ensure()` and sends `lexical.search` on the connection itself.
- **The fallback runs the daemon's own handlers.** `createVaultEntryServices(entries)` is the `vault`/`corpus`/`lexical` service map; the daemon registers it, and the in-process side calls the same map through a loopback link (`createInProcessLink`) over the process's own `VaultEntries`. A loopback failure is the wire's `DaemonRpcError`, as the daemon's registry would answer. The in-process client is the core over the loopback, with nothing left to adapt. This refines ADR-0020's "the fallback runs the same module" to "the fallback runs the same handlers".
- **One link per side per process.** The daemon side has the process's one connection; the in-process side has one loopback, built on first use and closed at teardown, which detaches it from every entry as a closed socket would.
- **Reads are views.** A view implements an interface the session already depends on over the client, and owns only the mapping to that interface's domain errors, which differ per interface. The semantic backend is `createSemanticBackendView(client, profile)`; the lexical reader becomes one in the same change's second PR (#193).
- **The embedding provider stays apart.** `DaemonEmbeddingProvider` is not a vault client. It shares the process's connection and switch; the same change's second PR moves its handshake onto the same epoch gate.

## Consequences

- **One error vocabulary on both sides.** Every read through the client, daemon or in-process, rejects with the protocol's codes (`NOT_ATTACHED`, `VAULT_UNAVAILABLE`, `CORPUS_NOT_READY` with its status, `CORPUS_FAILED`, `LEXICAL_FAILED`, `INVALID_PARAMS`, `INTERNAL`), and the in-process side validates the same params the daemon does, so a view that builds a bad param fails the same way in either. After the first PR that covers the corpus reads; the lexical leg's legacy readers keep wrapping every failure in `LexicalSearchError` until the lexical view replaces them, which keeps that wrapping with the same messages. An in-process caller of the semantic backend now sees a `DaemonRpcError` where it saw a raw error or a `VaultEntryError`, with the same message; the tools report the same outcome.
- **The cost of a new per-vault read** is the entry's own method, a service handler registered once in `createVaultEntryServices` (so both sides serve it), a `VaultMethods` row and a view. The adapters, the link, the attachment and the timeouts do not change: a method without its own timeout gets the default. `test/semantic/vault-client/new-read.test.ts` proves this, and typechecks: a row added by declaration merging reaches the entry through both adapters with no other change. A view of a new interface still needs its factory in `createVaultClients` and its field on `IRegisteredVault` for the tools to reach it.
- **Params take their wire shape in-process too**: a query vector is sent as `number[]`, a path set as an array. That is a copy of a few hundred numbers per anchor and of at most the vault's note list per read, accepted for one implementation.
- **ADR-0020's closing constraint becomes structural** once every reader is a view: a view has no connection, switch, attach or timeout of its own to add; it can only call the client. Until #193 completes, the legacy lexical readers still keep it by rule.
- **The embedding provider keeps its own facade.** It is process-wide and per profile, not per vault: it has no vault key and no attach, and its handshake also carries the batch size. On the client it would widen every vault's path with a vault-less call and provider state.
- **Delivered in two steps.** After the first PR, the client serves the semantic backend only. Until the second PR (#193), the lexical readers are the earlier facades over the vault's shared attachment, with their own switch consult and, on the daemon side, their own `lexical.search` request, so a vault still sends one `vault.attach` per epoch, and the loopback reads under the fixed id `LOCAL_CONNECTION_ID` that the legacy in-process lexical reader uses. `daemon status` is unchanged: in-process clients were never connections.

## Alternatives considered

- **A per-method in-process table over `VaultEntries`**: the second hand-kept copy of the daemon's services that this decision removes.
- **Splitting each service into validation and a shared operation layer both sides call**: the same effect as the loopback in more files, and the in-process side would skip the validation the daemon applies.
- **One loopback link per vault root**: per-root detach buys nothing, since the in-process entries never idle out and are disposed whole; one link per process keeps the fallback the shape of the daemon side.
- **The embedding provider on the client**: see Consequences; it shares the switch and, later, the epoch gate instead.
- **A runtime table of method descriptors (timeout, decoder)**: a second place to edit per method, which the default timeout makes unnecessary.
- **The status placeholders in each view**: every view would repeat what attaching in the background means.
