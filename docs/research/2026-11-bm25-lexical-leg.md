# BM25 for the lexical leg: whether, which, and how (November 2026)

The [embedding bake-off](2026-10-embedding-model-bakeoff.md) chose the semantic leg's model and the [agent-level A/B](2026-11-agent-ab-neuro-vault-vs-grep.md) measured what an agent gets from the whole server. This document looks at the other leg of `search_notes`: the hand-rolled lexical matcher ([`docs/architecture/lexical-search.md`](../architecture/lexical-search.md)), which ranks by six structural tiers and has no term weighting. It answers [issue #132](https://github.com/AlexMost/neuro-vault/issues/132) (bm25-style weighting or length normalisation on mixed corpora) and sets up the measurement [issue #131](https://github.com/AlexMost/neuro-vault/issues/131) asks for (lexical leg vs an FTS5 baseline on one golden set). Both are slices of the hosted-hub epic [#126](https://github.com/AlexMost/neuro-vault/issues/126).

Findings are as of 2026-11-01. Code citations are against `main` at `1450c51`. The numbers come from two kinds of probe run in one session on one machine (Apple M5, Node 24.13.0): the repo's own `rankNotes` on a hand-written three-note case, and a synthetic corpus shaped like the corporate vault for memory and timing. No production vault was read; no production code was changed. Library facts are checked against each project's own docs or source, with links in § Sources.

## TL;DR

- **Yes, add bm25-style weighting, but not a library and not SQLite.** Compute a BM25F-style score at scan time inside the existing `LexicalIndex` cache: term frequency, document frequency and note length are all available (or free to count) during the scan `rankNotes` already makes over every unit of every note. It needs **no postings index, no new dependency and no extra memory** beyond one integer per unit, keeps the mtime freshness model, the `allowed` pre-filter, the per-unit provenance, the multi-vault entry split and the RRF boundary exactly as they are. Size **M** (the scorer itself is S; the eval work and doc/ADR updates make it M).
- **The failure #132 hypothesises is real but is not "long notes rank high".** Run on the repo's own ranker, a short card loses to a long mirror page for three structural reasons: a heading hit anywhere in the long page beats a body hit in the card (tier order), AND-within-one-unit rewards long paragraphs (two unrelated words co-locate in a 4 000-character block, the card holding both words in two short adjacent blocks does not match at all), and density is measured against the matched unit, not the note, so a long page's five-word heading scores "density 1". Length normalisation is one third of the fix; field weights replacing the lexicographic tiers are the other two thirds. The fourth loss is recall, not ranking: prefix matching is query-side, so `платіжний` never finds `платіжного`, and no scorer fixes that.
- **Every ready-made option costs more than it gives at this scale.** On a synthetic 5 000-note corpus the current parsed cache is 42 MB of heap; MiniSearch adds 160 MB, Orama 276 MB, FlexSearch 390 MB, lunr 729 MB, and all but MiniSearch lose at least one of prefix-with-score, custom tokeniser or incremental update. SQLite FTS5 through `node:sqlite` is the strong alternative (45–79 MB outside the heap, 0.1–0.3 ms per query, bm25 with per-column weights, phrase and prefix in one engine), but it needs Node ≥ 22.13 while `engines` still admits 20.19 (Node 20 reached end of life on 2026-04-30, so that floor is due to move anyway), its `unicode61` tokeniser does not fold the apostrophe variants or `й`/`ї` the way `normalize.ts` does, its k1 and b are hard-coded, and in memory it is no smaller than the structures it would replace. It is the right engine past ~50 000 notes or once a boolean query language is wanted, not now.
- **Measure before merging, with the harness that exists.** The change is ranking-only (the candidate set does not move), so the read is MRR and hit@3 on `--pipeline lexical` and `--pipeline fused`, positional and production, before and after on one `vault_sha`, plus a per-query diff of `first_relevant_rank` on a labelled "card vs mirror page" subset. An FTS5 baseline for #131 is a ~150-line script over the same golden set and the same `eval/metrics.ts`; it costs half a day and should run first, because it also tells whether the corporate vault's losses are ranking (bm25 would help) or recall (it would not).

## 1. What the leg scores on today, and what breaks

### The scoring, in code

The leg is a scan, not an index. `rankNotes` ([`src/lib/obsidian/lexical/rank.ts:63-116`](../../src/lib/obsidian/lexical/rank.ts)) walks every note in the snapshot and, for every query, calls `matchUnit` on the title and on every unit. A unit is one mdast block: a heading, or a paragraph, code fence or table, with list items and blockquotes recursed into ([`blocks.ts:44-77`](../../src/lib/obsidian/lexical/blocks.ts)); the title is the file basename ([`blocks.ts:39`](../../src/lib/obsidian/lexical/blocks.ts)). A note's rank is decided by four keys in order ([`rank.ts:35-39`, `118-123`](../../src/lib/obsidian/lexical/rank.ts)):

1. **tier**, `kindBase + (phrase ? 0 : 1)` with title 0, heading 2, body 4 ([`rank.ts:30-33`](../../src/lib/obsidian/lexical/rank.ts)); the note takes its best unit's tier;
2. **density** of that best unit: matched characters divided by the **unit's** normalised length, capped at 1 ([`match.ts:47`, `67`](../../src/lib/obsidian/lexical/match.ts));
3. backlink count, descending;
4. path, ascending.

What is **not** in those keys:

- **No term frequency.** `indexAtBoundary` returns the first word-start occurrence and stops ([`match.ts:32-38`](../../src/lib/obsidian/lexical/match.ts)); a note that uses the term ten times scores like one that uses it once.
- **No document frequency.** Nothing in `rank.ts` or `match.ts` counts how many notes contain a token, so a near-stopword and a rare identifier weigh the same. The only vault-wide count is `perQueryTokenCounts`, computed on the failure path for AND-killed multi-token queries ([`rank.ts:133-148`](../../src/lib/obsidian/lexical/rank.ts)); it is exactly the per-token document frequency a bm25 needs, computed only when nothing matched.
- **No note length.** The density denominator is the unit, so note length never enters. A `ParsedNote` holds `title` and `units[]` with `raw`, `norm`, `lines`, `heading` ([`blocks.ts:8-19`](../../src/lib/obsidian/lexical/blocks.ts)) and no length field.
- **AND is per unit.** All tokens must sit in the same unit ([`match.ts:56-59`](../../src/lib/obsidian/lexical/match.ts)); a phrase is the whole normalised query at a word start in one unit ([`match.ts:43-51`](../../src/lib/obsidian/lexical/match.ts)). The design records this as the accepted trade-off D7 (`openspec/changes/archive/2026-07-05-hybrid-search-notes/design.md`), which also records why bm25 was rejected then: "needless on this corpus, non-deterministic across corpus changes, and requires a library (D5)". The corpus it was needless on was ~700 notes.
- **Prefix is query-side.** A token matches "at index 0 or after a non-word character; the end is free" ([`match.ts:29-31`](../../src/lib/obsidian/lexical/match.ts)). `пошук` finds `пошуком`; `пошуком` does not find `пошук`.

The order `rankNotes` produces is consumed as an order and nothing else: `fuseRanks` takes `lexical.notes.map((n) => n.path)` ([`src/modules/semantic/retrieval-pipeline.ts:158-164`](../../src/modules/semantic/retrieval-pipeline.ts)) and the response carries no lexical score by design ([`docs/architecture/rank-fusion.md`](../architecture/rank-fusion.md), "Fusion consumes only source ranks"). The daemon's `lexical.search` carries queries, `allowed`, `note_cap`, `per_note_cap` and nothing about scoring ([`src/daemon/protocol.ts:75-82`](../../src/daemon/protocol.ts)); the handler forwards them to the entry ([`src/daemon/services/lexical.ts:38-48`](../../src/daemon/services/lexical.ts)), which adds the graph's backlink counter ([`src/lib/vault-entry/vault-entry.ts:402-408`](../../src/lib/vault-entry/vault-entry.ts)). `allowed` narrows the candidate map before `rankNotes` sees it and never evicts from the cache ([`lexical-index.ts:88-93`](../../src/lib/obsidian/lexical/lexical-index.ts)).

Cost today is parse, not match: the first query over a cold cache reads and parses every note ([`lexical-index.ts:184-213`](../../src/lib/obsidian/lexical/lexical-index.ts)), which is where the corporate vault's 5.5 s first query and +427 MB RSS come from (the study's private notes, via #126); a warm two-token query over the 5 000-note synthetic corpus scans every unit in 18 ms.

### What breaks on a mixed corpus: a three-note case through the real ranker

The case is a short structured card whose body holds the answer, a long mirror page with many headings and a 5 300-character paragraph that mentions the words, and a second long page where the two words co-occur only because a paragraph is 4 000 characters long. The query words are deliberately absent from every title. Run through `parseNote` and `rankNotes` unchanged (script in the session scratchpad):

| query                                     | result                                                                                                         | why                                                                                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| phrase `налаштування платіжного шлюзу`    | **card first**, mirror page second                                                                            | both tier 4 (phrase in body); the card's 54-char unit has density 0.5, the mirror page's 5 304-char unit 0.005. Phrase queries already work.     |
| two tokens `налаштування платіжний`       | mirror page (heading), release page (body); **card absent**                                                   | the mirror page has both tokens in one heading (tier 3); the release page has both in one 3 988-char paragraph; the card has `платіжного`, which `платіжний` does not prefix. |
| one token `платіжний`                     | mirror page (heading) first, **card second**, release page third                                              | a one-word query is always a phrase, so the heading hit is tier 2 and the card's body hit tier 4, whatever the note is about.                                         |
| one token `шлюз`                          | mirror page first (heading + body), card second                                                                | same; the card's two body hits do not add up, only its best unit counts.                                                                        |

Three mechanisms, none of them "the note is long":

1. **Tier order is lexicographic.** A long page carries many headings, so it has many chances at tiers 2–3; a card's evidence usually sits in body text. No density can lift a body hit over a heading hit.
2. **AND-within-one-unit is a proximity proxy that scales with block length.** On the synthetic corpus the same two-token query returns 27 notes under unit-level AND and 142 under note-level AND. The 27 are not the 27 best; they are the notes with a block long enough to hold both words.
3. **Density normalises by the unit, not the note.** A heading of five words with the token in it has density ~0.2–1.0; a focused 50-character card paragraph has 0.1–0.2. The signal reads "the matched block is short", not "the note is about this".

A fourth loss is recall, and no scorer touches it: **prefix matching is query-side only**. A query in the nominative (`платіжний`) misses the genitive in the text (`платіжного`); the reverse works. The agent-level A/B already listed the substring/whole-word side of this ([`2026-11-agent-ab-neuro-vault-vs-grep.md`](2026-11-agent-ab-neuro-vault-vs-grep.md), "What this suggests", item 1). The fix is on the query side (trim a query token to a stem-length prefix, or a light Ukrainian suffix stripper applied to both sides) and is independent of weighting.

So #132's hypothesis holds in effect but not in mechanism: long mirror pages outrank short cards because they have more units, more headings and longer paragraphs, not because length is rewarded. **Length normalisation alone would fix the third mechanism only.** Field weights (BM25F) that replace the lexicographic tiers fix the first; a note-level AND with a unit-level proximity or phrase bonus fixes the second and is a separate, larger change.

## 2. Options

### Measured on one synthetic corpus

5 000 and 50 000 generated notes with the corporate vault's shape (median 260 / mean 381 / p90 855 words, 58 % Cyrillic, pseudo-Ukrainian stems × suffixes under a Zipf law so prefixes expand like inflections, headings every few paragraphs, frontmatter). `heap` is V8 heap after a forced GC, build to query-ready, minus the loaded corpus; SQLite's memory lives outside the heap and is reported as `page_count × page_size`. The query is the same two five-character Cyrillic prefixes AND-ed, title weighted where the engine allows. Timings are medians of 20 warm queries. The corpus is synthetic: use the ratios, not the absolute numbers (the real vault's parsed cache is several times larger than the synthetic one because of wide tables and link-heavy pages).

Two things to read off this table for the hub: the current cache is the cheapest structure that holds the text at all (every index comes **on top of** the parsed units, because provenance and snippets need them), and FTS5 is the only candidate whose memory can be decoupled from corpus size, by backing it with a file and a bounded page cache (the 5 000-note file-backed run held 8 MB of RSS over a 60 MB database). The JavaScript indexes cannot be paged out.

Two cross-cutting facts from the survey matter for the decision. First, **a Ukrainian stemmer now exists** (Snowball added one; `multilingual-stemmer` 2.2 and `@orama/stemmers` ship it), so "stem both sides and match exact stems" is a real alternative to query-side prefixes, independent of which engine scores. Second, none of the ready-made engines knows the document structure this leg reports: all of them need the parsed units kept alongside for `matched_in`, `lines`, the nearest heading and snippets, so every index in the table is additional memory, never a replacement for the cache.

## 3. Integration shape that keeps what works

### Where the score enters

**Replace the within-leg ordering; do not add a weight before RRF.** `fuseRanks` consumes ranks, not scores ([`rank-fusion.md`](../architecture/rank-fusion.md)), so a better lexical order is a better fused order with no change to the merge, the adaptive `k`, the `EXPANSION_WEIGHT` tuning, the response contract (no numeric score on `lexical[]`, [`docs/guide/finding-notes.md`](../guide/finding-notes.md)) or the wire ([`protocol.ts:75-90`](../../src/daemon/protocol.ts)). A fusion-level lexical weight was considered in `rank-fusion.md` ("Further per-source weights") and deferred pending data; this change does not need it.

### The scorer

Candidate generation stays as it is: `matchUnit` decides whether a unit matches (phrase, else all tokens at word starts), and each matching unit remains an evidence row with `matched_in`, `lines`, `heading` and a lazily built snippet ([`rank.ts:67-114`](../../src/lib/obsidian/lexical/rank.ts)). Only the **ordering keys** change, from `(tier, density, backlinks, path)` to `(score, backlinks, path)` with

```
tf_{t,f}  = word-start occurrences of token t in field f (title | heading | body), summed over the note's units of that field
tf_t      = Σ_f w_f · tf_{t,f}                                  (BM25F: weight before saturation)
len       = Σ_units tokens(unit) + tokens(title);  avglen over the ranked set
tf̃_t      = tf_t / (1 − b + b · len / avglen)
idf_t     = ln(1 + (N − df_t + 0.5) / (df_t + 0.5))              (Lucene form, never negative)
score_q   = Σ_t idf_t · tf̃_t · (k1 + 1) / (tf̃_t + k1)  ×  (1 + p · [some unit holds q as a phrase])
score     = max over the call's queries q that matched the note
```

with `k1 = 1.2`, `b = 0.75`, starting weights `w_title = 4`, `w_heading = 2`, `w_body = 1`, `p = 0.5`, all to be tuned on the harness (§ 4). Where every number comes from:

- `tf`: `indexAtBoundary` ([`match.ts:32-38`](../../src/lib/obsidian/lexical/match.ts)) already loops over occurrences; it stops at the first word-start hit. Continuing the loop to count them is the same O(unit) scan the matcher makes now.
- `df_t` and `N`: `rankNotes` visits every note of the ranked set for every query already; counting the notes where a token matched **anywhere** (not only the AND survivors) is the per-token count `perQueryTokenCounts` computes today on the failure path ([`rank.ts:133-148`](../../src/lib/obsidian/lexical/rank.ts)), moved to the main path. Because the prefix match is the unit of matching, `df` of a prefix is naturally "notes with any word starting with it", which is the right idf for a prefix query (a two-letter prefix matches everywhere and weighs nothing).
- `len`: one `tokens` integer per unit, counted once at parse time in `parseNote` ([`blocks.ts:38-82`](../../src/lib/obsidian/lexical/blocks.ts)); the only cache growth. `avglen` is a sum over the ranked set per call.
- `N` and `df` are computed over the **ranked set** (after `allowed`), not the whole scope: it keeps a filtered call's cost bounded by the filter, and "rare within this folder" is the right notion when the caller asked for this folder. (`totalNotes` for the adaptive `k` stays pre-filter as today, [`lexical-index.ts:102`](../../src/lib/obsidian/lexical/lexical-index.ts).)

Two shapes to A/B, because they answer the three mechanisms of § 1 differently:

- **Shape 1, score within tiers.** Keep `tier` as the first key; the score replaces `density`. Fixes mechanism 3 only. Safe for name lookups (a title hit still always wins) and a small diff.
- **Shape 2, one fielded score.** Tiers become the `w_f` weights and the phrase bonus. Fixes mechanisms 1 and 3. A title phrase with `w_title = 4` and `p = 0.5` still dominates in practice, but a focused card can now beat a passing heading mention in a long page. This is the shape the corporate vault needs; the harness decides whether it costs anything on the personal vault's name queries.

Mechanism 2 (AND within one unit) is out of this change's scope. The natural follow-up is note-level AND with the unit-level co-location kept as a bonus (`p` for phrase, a smaller bonus for all tokens in one unit); the 27-vs-142 gap on the synthetic corpus says it changes recall far more than any re-weighting, so it deserves its own measurement.

### What stays byte-identical

- **Determinism.** The score is a pure function of the ranked set, with `backlinks` and `path` still breaking ties; the same query on an unchanged vault gives the same `matches[]`. D7's objection ("non-deterministic across corpus changes") describes any corpus-dependent statistic, backlink counts included; the property the tests pin is reproducibility on a fixed vault, and that holds.
- **Provenance.** Evidence rows are still per unit with `lines` and the nearest heading; `perNoteCap` keeps the strongest rows, now sorted by their unit's contribution instead of `(tier, density)` ([`rank.ts:151-158`](../../src/lib/obsidian/lexical/rank.ts)).
- **Pre-filters.** `path_prefix`, `tags`, `frontmatter` arrive as `allowed` and are applied before ranking ([`lexical-index.ts:88-93`](../../src/lib/obsidian/lexical/lexical-index.ts)); unchanged.
- **Multi-vault.** One `LexicalIndex` per vault entry ([`vault-entry.ts:402-408`](../../src/lib/vault-entry/vault-entry.ts)) gives per-vault statistics for free; fan-out fuses per vault ([`fan-out.md`](../architecture/fan-out.md)), so no cross-vault idf is needed or wanted.
- **The daemon's lexical service.** No change to `lexicalSearchParams`, `LexicalSearchResult` or the handler ([`lexical.ts:34-57`](../../src/daemon/services/lexical.ts)): ranking is the entry's, as the handler's comment says. The view and standalone readers and their parity tests ([`test/semantic/lexical/parity.test.ts`](../../test/semantic/lexical/parity.test.ts)) stay valid because all three sides run the same `rankNotes`. The frozen oracle `test/lib/obsidian/lexical/_legacy-lexical-index.ts` pins the old order and will need re-pinning in the same PR.
- **Memory and freshness.** One integer per unit; no postings, no watcher coupling, no second cache. The hub's planned split of lexical scope from resolution scope (#126, slice 3) keeps working because there is still exactly one structure to scope.

### If FTS5 is chosen later

The shape that preserves provenance is **one FTS5 row per unit**, not per note: `(note_id, kind, line_start, line_end, norm_text)` in an external-content table, `detail=full` (phrase and `NEAR` need it; `detail=column` was 100× slower on prefix queries in the probe anyway), `prefix='2 3 4 5'` if query latency matters more than 35 MB, text inserted **already normalised** by `normalize.ts` so apostrophes and `й`/`ї` behave as today and `highlight()` offsets fall in normalised coordinates, which `makeSnippet`'s offset map already projects back ([`snippet.ts`](../../src/lib/obsidian/lexical/snippet.ts)). The query is built per token as `"tok"*` joined with `AND` (an unquoted `об'єкт` is a syntax error in FTS5's query language). `bm25(fts, w_title, w_heading, w_body)` scores units; aggregate per note with `max` or a sum, keep the top units as evidence rows. The refresh that today re-parses a changed note deletes and re-inserts its rows in one transaction. `allowed` becomes a `JOIN` on the notes table. Two FTS5 properties shape the scorer: `k1` and `b` are hard-coded (1.2 / 0.75), so only the column weights are tunable, and a prefix token is one phrase whose idf is pooled across its expansions (a two-letter prefix that matches most rows scores near zero), which is the right behaviour for stem-prefix queries. The cost is the Node floor: `node:sqlite` exists from Node 22.5, lost its flag in 22.13 / 23.4 and is stability 1.2 "release candidate" from Node 24.15 / 25.7; Node 20 has no SQLite binding, and `engines` still admits `^20.19.0` ([`package.json`](../../package.json)). Node 20 reached end of life on 2026-04-30 and Node 22 is in maintenance until 2027-04-30, so raising the floor is a reasonable major, but it is a decision of its own; `better-sqlite3` 13 (native addon, prebuilt binaries, Node ≥ 22) or `@sqlite.org/sqlite-wasm` are the alternatives if it is not taken, and `sql.js` is not one (no FTS5).

## 4. How to measure

The harness ([`eval/README.md`](../../eval/README.md)) already runs the production pipeline over a golden set, including `--pipeline lexical` through the standalone reader ([`eval/pipelines.ts:86-91`](../../eval/pipelines.ts)), reports MRR, hit@3, recall@10, control hit rate, and a per-query `first_relevant_rank`, and refuses to compare reports across `vault_sha`s. Nothing new is needed to measure Shape 1 and Shape 2; the discipline is in the golden set and the runs.

1. **Golden sets.** The personal vault's 25-query set (21 `ua` / 4 `en`; the bake-off's set) guards against regressions on name lookups. The corporate vault's set (14 queries today, #131: lexical MRR 0.167 / hit@3 0.167) is the one that should move; extend it by the 10–15 realistic entries #131 asks for, and make sure **at least eight entries are of the failing class**: the labelled answer is a short card and a long mirror page also matches the words. Give them an id prefix (`m0xx`) so the per-query diff can be read by class without changing the harness's fixed `class` set. The agent-level study's Vault B set (30 answerable + 5 controls) is a third source once an owner has reviewed its 11 low-confidence rows.
2. **A switch, not two branches.** Put the scorer behind an environment variable for the experiment (`NEURO_VAULT_LEXICAL_SCORER=tiers|bm25-tiers|bm25f`) so before and after share one `code_sha` and one process; remove the switch when the decision is made. The harness records `config`, so add the scorer name there.
3. **Runs.** On each vault, at one clean `vault_sha` with a fresh corpus, the harness's own baseline matrix: `--pipeline lexical` positional and production, `--pipeline fused` positional, production quick and production deep, for each scorer value. Fifteen runs per vault; minutes each.
4. **Read.** Scoring is ranking-only, so the candidate set does not change and controls cannot get noisier; the read is **MRR** and **hit@3** on `lexical` (the pure effect) and on `fused` production deep (what an agent gets), per `lang`, plus the paired diff of `first_relevant_rank` on the `m0xx` entries. `recall@10` moves only through the pool cap and is a sanity check.
5. **Stop criterion.** Adopt the scorer that, on the corporate set, raises `lexical` positional MRR by **≥ 0.05 absolute** (one query in twenty moving from rank 2 to 1, or from a miss to rank 3) with hit@3 not lower, and on the personal set lowers neither MRR nor hit@3 by more than one query on any `lang` slice; and that leaves `fused` production deep no worse on both. Below that, keep the tiers and spend the effort on the recall items instead. The guard is one query because the sets are small; direction across both vaults matters more than the second decimal.
6. **Cost.** First-query time and RSS on the corporate vault before and after, by hand, as a percentage in the PR (the integer per unit should be invisible; the extra occurrence counting should stay within the scan's current cost).

### The FTS5 baseline for #131

Cheap, and it should run first, because it answers the question #132 defers to it ("decide after #131"): are the corporate vault's lexical losses ranking or recall?

- A ~150-line script in the session scratchpad, the bake-off's precedent: `FsVaultReader` + `loadVaultScope` for the scoped listing, `splitFrontmatter`, an in-memory `node:sqlite` FTS5 table (`unicode61 remove_diacritics 2`, `detail=full`) with title and body columns, the golden set loaded by `eval/golden.ts`, and `scoreQuery`/`aggregate` from [`eval/metrics.ts`](../../eval/metrics.ts) so the numbers are the harness's numbers. Node ≥ 22.13.
- Two query forms per entry: exact tokens AND-ed (the sister server's behaviour) and `"tok"*` prefixes AND-ed (FTS5 with neuro-vault's prefix rule), bm25 with title weight 5. A query array runs as one `OR` of per-string groups.
- Report MRR / hit@3 / recall@10 per `lang` and `class` next to the lexical runs, and per query: where FTS5 wins with the **same candidate set** the loss is ranking and bm25 in the leg will recover it; where FTS5's exact form loses on a Ukrainian query and the prefix form wins, the leg's prefix rule is confirmed; where both FTS5 forms find a note the leg misses, it is recall (query-side prefix asymmetry, or AND-within-unit) and no scorer helps.
- Promote the script to `--pipeline fts5` in the harness only if the baseline is to be re-read regularly; a one-off comparison belongs in this `docs/research/` folder with aggregate numbers only (no query text or note paths leave the vault, per the harness's rule).

## 5. Recommendation

**Do it: BM25F-style scoring at scan time inside `rankNotes`, Shape 2 as the target and Shape 1 as the fallback, decided by the harness.** No library, no SQLite, no new cache. Size **M**: the scorer, the switch and the test re-pin are a day; the two golden-set extensions, fifteen runs per vault, the FTS5 baseline script and the doc updates (`lexical-search.md` § 6 and "What it deliberately does not do", `rank-fusion.md`'s "within-leg density" sentence, an ADR superseding D7's bm25 line) are the rest. It is a capability change to the ranking contract in spirit if not in schema, so it goes through an opsx change; the FTS5 baseline for #131 can be a direct research PR like this one.

Main risks, with the mitigation each has:

1. **The corporate losses are recall, not ranking.** The probe's fourth mechanism and the 27-vs-142 gap say a good share of them may be. Mitigation: run the FTS5 baseline first (half a day) and read the per-query split before building the scorer; if recall dominates, the next change is query-side stem trimming and note-level AND, and this scorer still lands as a smaller win.
2. **Shape 2 hurts name lookups on small personal vaults.** A heading in a hub note could outrank an exact title on a short-titled card. Mitigation: the personal set's `name` slice is the guard; Shape 1 is the fallback; `w_title` is a knob.
3. **Prefix df makes short query tokens weightless.** `про*` expands to half the vault and gets idf ≈ 0, which is correct for ranking but surprising when the whole query is one short token: every candidate then ties on score and falls to backlinks and path. Mitigation: today's density is no better there; keep a minimum idf floor if the harness shows ties.
4. **Scan cost grows with counting.** Counting every occurrence instead of stopping at the first roughly doubles the per-unit work on matching units only; the 50 000-note synthetic scan is the bound to watch (table above). Mitigation: measure in the PR; if a 50k vault is on the roadmap before the hub's lexical-scope split lands, FTS5 is the escape hatch and § 3 already describes its shape.
5. **Parity fixtures.** The frozen pre-move oracle and the rank tests pin the old order; they move with the scorer in the same PR, and the eval runs are the evidence the new order is better, not the tests.

Revisit the engine question, in favour of FTS5 through `node:sqlite`, when any of these becomes true: the hub serves more than ~50 000 notes in one lexical scope, a boolean query language is wanted at the tool boundary, or Node 20 is dropped for another reason.

## Open questions

- **Which `b`?** 0.75 is the textbook value for whole documents; with per-field tf the heading field is short by construction and may want a smaller `b` or none. The harness can try `b ∈ {0.3, 0.5, 0.75}` in one afternoon.
- **Per-query max or sum across a query array.** Today a note's tier is its best across queries; `max` keeps that meaning, `sum` rewards notes that answer several synonyms. RRF already rewards agreement across legs, not across queries of one leg, so this is worth one run.
- **Stem trimming or a real stemmer.** The cheapest fix for the `платіжний`/`платіжного` asymmetry is to also try each query token trimmed by its last one or two letters when it is longer than five. The principled one is Snowball's Ukrainian stemmer (`multilingual-stemmer` on npm) applied to both sides, which would replace query-side prefixes with exact stem matches and change what `matched_in` snippets highlight. Both widen recall at the price of precision and belong with the note-level-AND measurement, not here.
- **A `lexical_score` on the wire.** The no-score invariant (D3/D10) is deliberate; the eval reads order, so nothing needs the number. If a future reranker stage wants it, it should be added as a separate field, not folded into `similarity`.
